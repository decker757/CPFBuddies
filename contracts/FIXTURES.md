# Fixtures

Generated by `python -m trustrail.contracts.export`. Each fixture is a complete `VerificationRequest` and the verdict the Verifier must return for it. The table below is produced by running the Verifier over them, so it cannot drift from actual behaviour.

| Fixture | Decision | Reason codes | What it proves |
| --- | --- | --- | --- |
| `clean_pass` | **PASS** | — | The happy path. A toothbrush at S$4.20 against a S$5.00 mandate, from a registered merchant, with a low risk score. |
| `cap_boundary_exact` | **PASS** | — | A charge for exactly the cap settles. The cap is a limit, not a budget to stay under, and the comparison is exact — no rounding slack in either direction. |
| `approved_after_review` | **PASS** | — | A mandate a human approved during REVIEW: merchant and basket are now bound and the mandate re-signed. It re-enters the Verifier and passes every check again — approval supplies more to verify, it does not skip verification. |
| `product_substitution` | **REVIEW** | `RISK_SCORE_REVIEW_BAND`, `INTENT_MISMATCH_SUSPECTED` | Right price, wrong product. This is the gap left by minting the mandate before the product was chosen, and it is why the Evaluator exists. A human decides. |
| `low_price_new_seller` | **REVIEW** | `RISK_SCORE_REVIEW_BAND`, `SUSPICIOUS_SELLER_PRICING` | A brand new seller pricing far below market inside an otherwise legitimate marketplace. Neither signal alone is damning, which is exactly why this is a REVIEW rather than a FAIL. |
| `prompt_injection_in_listing` | **FAIL** | `RISK_SCORE_CRITICAL`, `INJECTION_SUSPECTED` | THE demo. The listing description carries instructions aimed at the agent. The Evaluator flags it and scores it 9, which is above the review band, so the charge fails without a human. Note that even if the Evaluator had been fooled, the cap and expiry still held. |
| `tampered_cap_resigned_digest` | **FAIL** | `MANDATE_SIGNATURE_INVALID` | An attacker raises the cap from S$5 to S$5000 and honestly recomputes the digest — the hash is public, so they can. What they cannot do is produce the issuer's signature over it. This is the check the whole design rests on. |
| `tampered_cap_stale_digest` | **FAIL** | `MANDATE_DIGEST_MISMATCH` | The lazy version of the same attack: edit the cap and leave the original digest in place. Caught one check earlier. |
| `forged_evaluator_verdict` | **FAIL** | `EVALUATOR_SIGNATURE_INVALID` | A compromised Browser Agent writes itself a clean risk score and signs it with its own key. The Agent Registry knows which key the Evaluator uses, so the forgery does not verify. |
| `replayed_evaluation` | **FAIL** | `EVALUATOR_SUBJECT_MISMATCH` | A genuine, correctly signed low-risk evaluation — but it was produced for a different basket. Without the subject binding, signing the evaluator's output would buy nothing. |
| `over_cap` | **FAIL** | `CHARGE_OVER_CAP` | S$7.50 against a S$5.00 mandate. Arithmetic, not judgement: no approval button, no override. Spending more needs a new mandate. |
| `one_minor_unit_over_cap` | **FAIL** | `CHARGE_OVER_CAP` | The cap plus 0.000001 XSGD. Amounts are compared as integer minor units, so there is no rounding slack to hide a charge in. |
| `expired_mandate` | **FAIL** | `MANDATE_EXPIRED` | The same clean charge, arriving after the approval window closed. A mandate the buyer approved ten minutes ago is not consent now. |
| `revoked_mandate` | **FAIL** | `MANDATE_REVOKED` | The buyer pulled the mandate before settlement. |
| `already_consumed` | **FAIL** | `MANDATE_ALREADY_CONSUMED` | A replay of a charge that already settled. Mandates are one-time; the second attempt has nothing left to spend. |
| `kill_switch_engaged` | **FAIL** | `KILL_SWITCH_ACTIVE` | The panic button is down. Nothing settles for this buyer. |
| `unsettleable_currency` | **FAIL** | `CURRENCY_NOT_SETTLEABLE` | A mandate denominated in fiat SGD rather than XSGD. This rail settles XSGD on Avalanche C-Chain and nothing else. |
| `payout_address_redirected` | **FAIL** | `PAYOUT_ADDRESS_MISMATCH` | A scam seller inside a registered marketplace supplies its own payout address in the listing. XSGD only ever goes to the address the platform registered, so the money path is closed regardless of what the listing claims. |
| `unregistered_merchant` | **FAIL** | `MERCHANT_NOT_REGISTERED` | The counterparty is not in the Merchant Registry at all. We verify platforms, and an unverified platform is not a counterparty. |
| `basket_swapped_after_approval` | **FAIL** | `BASKET_BINDING_MISMATCH` | A human approved one basket during REVIEW; a different basket arrives at settlement. Once bound, the basket cannot change underneath the approval. |
